# ADR-0003: シークレット管理の検証と防御策修正

- **Status**: Accepted
- **Decision**: AWS Systems Manager Parameter Store Standard tierを採用し、アプリケーション側の検証と運用監査で補完する。

## 背景

認証情報をソースコードへ保存しないため、SSM Standard、SSM Advanced、AWS Secrets Manager、`.env`、Vaultを比較した。比較軸は月額コスト、個人ローカル運用の複雑さ、アクセス制御、ローテーションの実現性である。

| 選択肢 | コスト | 運用・ローテーション | 判断 |
| --- | --- | --- | --- |
| SSM Standard | 低い | 手動ローテーションと期限監視を組み合わせる | 採用 |
| SSM Advanced | 高い | 高度な機能はあるが、この規模では過剰 | 不採用 |
| Secrets Manager | 高い | 対応サービスでは自動ローテーション可能 | 不採用 |
| `.env` | 低い | ローカル開発には有用だが、共有・監査に弱い | 開発時のみ |
| Vault | 運用負荷が高い | 高機能だが単独ローカル運用には過剰 | 不採用 |

## 検証からの設計修正

当初は、IAMの`ssm:Tier`条件でAdvanced tierを拒否する案を想定した。しかし実AWSで検証した結果、この条件は利用できないことが分かった。

**AIが提案 → 実AWSで検証 → 提案の一部が誤りと判明 → 設計を修正**という流れを採用し、使えないIAM条件への依存を撤回した。代わりに、登録処理でStandard tierを強制し、設定検証とコスト監視を重ねる防御へ変更した。

## 結果

シークレット値はリポジトリに保存しない。運用時は実行時取得、開発時はGit管理外のローカル環境変数とし、定期的な期限確認と監査ログで運用する。
